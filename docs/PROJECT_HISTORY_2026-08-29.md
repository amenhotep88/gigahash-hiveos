# GigaHash HiveOS — история проекта

Дата фиксации: **2026-08-29 UTC**.

## 1. Исходная задача

Проект начался как проверка официального GigaHash NOCK ZK CUDA miner на RTX 3070/3070 Ti и перенос его в HiveOS. Основные ограничения:

- большинство GPU подключены через PCIe x1 risers;
- часть ригов имеет слабые CPU, мало RAM или HiveOS на USB;
- официальный CDN и GitHub release assets периодически недоступны с HiveOS;
- официальный miner — закрытый бинарник без исходного CUDA-кода;
- пользователь работает пошагово и проверяет команды непосредственно на ригах.

## 2. v1.6: первый рабочий HiveOS package

Создан репозиторий `amenhotep88/gigahash-hiveos` и release `v1.6-hiveos`.

Первый пакет реализовал:

- `h-manifest.conf`, `h-config.sh`, `h-run.sh`, `h-stats.sh`;
- передачу server, payout address, worker и extra args;
- установку и запуск официального `gigahash-zk-12.9`;
- отображение proof/s через HiveOS hash-rate fields.

Первый практический сбой: HiveOS добавлял worker suffix к `%WAL%`, и miner получал неверный payout. Исправление: payout оставлен статическим адресом, worker передаётся отдельным аргументом; wrapper защитно удаляет matching suffix.

## 3. Ранние тесты оборудования

- 6× RTX 3070: примерно `22.82–23.89 kp/s`, или `3.76–3.85 kp/s/GPU`.
- Потребление в одном раннем срезе: около `58 W/GPU`, VRAM около `5.6/8 GiB`.
- RTX 3070 Laptop: краткие пики выше, стабильный ориентир ранней версии около `3.8 kp/s/GPU`.
- PCIe x1 оказался пригоден; он мог отнимать несколько процентов при масштабировании, но не делал майнинг невозможным.
- На слабом CPU и 4 GB RAM запуск требовал контроля OOM; многократные instances могли завершаться `exitcode=137`.

| Git | Содержание |

| `a5f4898` | jsDelivr mirror parts для restricted HiveOS rigs |

Ключевое инфраструктурное решение v1.8: официальный бинарник скачивается один раз при подготовке релиза, упаковывается воспроизводимо, режется на части для jsDelivr и при запуске собирается обратно с обязательной проверкой SHA-256 архива и бинарника.

Это решило проблему недоступности официального CDN на части ригов, не подменяя происхождение бинарника: источником остаётся официальный GigaHash release.

## 5. Исторический split NOCK+PRL

Временно разрабатывался отдельный wrapper для `redrig`, который запускал GigaHash NOCK на GPU 0–3 и SRBMiner PearlHash/PRL на GPU 4–7. Были исправлены:

- поиск `srbminer_custom_bin` внутри vendor archive;
- загрузка SRBMiner через jsDelivr parts;
- раздельные процессы и корректное завершение peer process;
- объединённая HiveOS-статистика;
- SRB API на `127.0.0.1:21550`.

Основные коммиты: `7e49f0b`, `74f9c56`, `9dc1d29`, `932f72b`, `efba40b`.

**Решение 2026-08-29:** split закрыт и удалён из текущего проекта и GitHub Releases. Git-история сохранена. SRBMiner/PRL не являются текущей частью проекта и не должны автоматически возвращаться.

Наблюдаемый результат v1.9 на Peladn:

|---|---:|---:|---:|
| v1.8, 8 GPU | `36.49 kp/s` | `4.56 kp/s` | `4.26` |

Обычный режим v1.9 уже включал крупную оптимизацию CPU. Дополнительный `--low-cpu` снижает CPU ещё сильнее ценой хешрейта и роста VRAM. При тесте с этим флагом несколько ригов сначала майнили, затем завершались, выводя только `E`. Контрольный запуск Peladn без флага работал с высоким хешрейтом и низкой нагрузкой. Итог: не включать `--low-cpu` по умолчанию.

## 7. Разговор с разработчиком официального miner

Разработчику переданы контролируемые наблюдения по производительности PCIe:

- Gen3 x16: около `4.71 kp/s` на RTX 3070 в v1.8;
- Gen1 x1, 4 GPU: около `4.68 kp/s/GPU`;
- Gen1 x1, 8 GPU: около `4.56 kp/s/GPU`;
- traffic Gen1 x1 был импульсным: RX `20–171 MB/s`, TX `3–37 MB/s`.

Гипотеза сформулирована осторожно: профилировать latency, small transfers, synchronization, batching, pinned memory и overlap H2D/D2H с CUDA. Неполная средняя загрузка PCIe сама по себе не означает линейный резерв хешрейта.

Разработчик уточнял, не запускается ли отдельный miner process на каждую GPU из-за фиксированного расхода RAM на процесс. Проверка: на каждом риге работает один GigaHash process на все 6/8 GPU; `--instances 2` — внутренние GPU-инстанции, не OS processes.

## 8. Пул и первая подтверждённая экономика

Baseline 2026-08-27 22:10 UTC:

- 5 workers / 26 GPU;
- `110.762 kp/s`;
- available `843.8677 NOCK`;
- pool estimate `$32.27/day`;
- acceptance `98.97%`.

После перевода всех восьми GPU redrig на обычный v1.9:

- 5 workers / 30 GPU;
- около `138–140 kp/s`;
- acceptance около `99.3%`.

Первая зафиксированная выплата 2026-08-28: `2549.3939 NOCK`. Важная техническая поправка: API использует `65,536 nicks` на `1 NOCK`, а не десятичные `100,000`.

## 9. Текущая модель развития

Проект больше не расширяется дополнительными алгоритмами. Цикл поддержки:

1. ждать новый официальный GigaHash binary;
2. проверить источник, версию, CLI и checksum;
3. провести короткий ручной A/B на одном риге;
4. обновить wrapper constants, mirror parts, package version и tests;
5. пройти release workflow;
6. постепенно развернуть на остальных ригах;
7. обновить handoff.
