Используй навык `gigahash-mining-operations`. Это аналитическая задача: ничего не арендуй, не продлевай, не отменяй, не устанавливай и не меняй на серверах без отдельного явного разрешения пользователя непосредственно перед действием.

## Постоянные данные и цель

- GigaHash payout-адрес: `W1ijDJZsLuKiLpKWzr5LYeVMnJKF8Khx9stXEBoXQfxwjEotbxppbN`.
- География аренды: RU/UA/EU; US исключить.
- Обычная аренда: только USD on-demand, цена всего сервера `price.usd.on_demand_usd` за сутки. Spot, BTC и CLORE не подменяют эту цену.
- Приоритет: надёжный multi-GPU риг, консервативная чистая прибыль от `$5/day`, желательно маржа `40%+`, доступность минимум 24 часа. Не показывай варианты ниже `$1.5/day` conservative net без отдельного разрешения.

## Порядок работы — не смешивай этапы

### Этап 1. Проверка источников

Сначала зафиксируй UTC-время и получи все входные данные. Не начинай ранжирование рынка, пока не сообщишь, какие источники подтверждены.

1. **GigaHash API — основной источник.** Используй только:
   - `https://gigahash.cloud/api/v1/info`;
   - `https://gigahash.cloud/api/v1/pool`;
   - `https://gigahash.cloud/api/v1/gateways`;
   - `https://gigahash.cloud/api/v1/miners/W1ijDJZsLuKiLpKWzr5LYeVMnJKF8Khx9stXEBoXQfxwjEotbxppbN`;
   - связанные `/hashrate-history`, `/shares?limit=N`, `/payouts?limit=N`;
   - `https://gigahash.cloud/api/v1/hashrate-history` только как историю **пула**, не сети.
2. Перед браузером выполни один полный повтор точного API через IPv4/HTTP1.1:

   ```bash
   curl -4 --http1.1 --compressed -fsS \
     --connect-timeout 10 --max-time 25 \
     --retry 2 --retry-all-errors \
     -H 'Accept: application/json' URL
   ```

   Проверяй непустой body, валидный JSON и ожидаемые поля. `HTTP 200` с пустым body — ошибка транспорта/прокси. Не перебирай придуманные endpoint-ы.
3. Если точный API после полного повтора недоступен, используй **CometFox (Camoufox runtime)** для открытия тех же официальных API/UI. Пиши: `direct API unavailable from this environment; official data obtained through CometFox`, а не «пул работает только через браузер». Данные помечай `browser-observed`.
4. **Цена продажи NOCK:**
   - сначала SafeTrade ticker и `nockusdt` order book через официальный API;
   - при `522/403` — один повтор, затем SafeTrade через CometFox;
   - цена считается исполнимой только по bid-side VWAP на ожидаемый объём продажи с учётом trading fee и slippage;
   - Kraken или другая биржа может стать исполнимым источником только после одновременного подтверждения: торговой пары, свежего стакана и его объёма, доступности аккаунту пользователя, открытого депозита, совместимости сети выплаты GigaHash с сетью депозита либо рабочего моста, а также всех bridge/deposit/trading costs;
   - один ticker `best bid` без этих проверок — только `reference`, не исполнимая цена;
   - CoinGecko и другие агрегаторы — только контрольная цена.
5. Если исполнимой цены нет, разрешён только предварительный сценарий по `$0.025/NOCK` с явной пометкой `НЕ ПОДТВЕРЖДЕНО ДЛЯ АРЕНДЫ`. Всегда показывай break-even цену.

После этапа 1 дай короткую строку: `pool source / price source / price status / Clore source / snapshot UTC`.

### Этап 2. Все воркеры и действующие аренды

1. Получи все записи payout-адреса, но не называй все строки активными воркерами.
2. Раздели активные сейчас, offline/исторические и возможные дубликаты/старые сессии.
3. Для активности используй официальный `online/status`, а при его отсутствии — свежесть `last_seen` относительно штатного интервала обновления. Укажи выбранный порог.
4. Сверь account-level `connected_workers` с фактически перечисленными активными именами, сумму их hashrate — с account total, а GPU online/total — с карточками воркеров. Любое расхождение покажи отдельно.
5. Покажи **каждый** активный worker: имя, owned или `clore-*`, версия, hashrate, GPU online/total, last_seen/age, uptime, estimated NOCK/day и USD/day, если цена подтверждена.
6. Через авторизованную страницу Clore **My orders** получи все активные заказы и сопоставь их по server ID с `clore-SERVER_ID` на пуле:
   - `ACTIVE + worker fresh` — работает;
   - `ACTIVE + worker missing/offline` — авария и возможное продолжение списаний;
   - `CLOSED/EXPIRED + old offline worker` — нормальная история;
   - `pool offline` без проверки My orders не означает, что аренда закончилась.
7. Не делай общий вывод «все clore offline», пока не покажешь имена, last_seen и статус соответствующего заказа.

Сначала закончи и выведи эту сверку. Только затем переходи к поиску новых ригов.

### Этап 3. Сеть, пул и доходность

1. Из `/api/v1/info` возьми комиссию пула.
2. Из `/api/v1/pool` возьми `network_targets.zk.expected_blocks_per_unit_work = p`, `generated_at`, `observed_at` и node height.
3. Рассчитай текущий network ZK hashrate: `network_ZK_proofs_per_second = 1 / p / 214`.
4. Pool ZK hashrate считай отдельно: сумма `zk.accepted_work_per_second` только для gateway с `online=true` и `node_healthy=true`. Не называй его hashrate сети.
5. Текущий NOCK/kp/s/day рассчитывай по официальной формуле из `gigahash.cloud/app.js`, включая reward, fee и proof-survival. Перепроверь результат по известному активному worker.
6. Рост/падение сети за 24/48 часов утверждай только по двум timestamped snapshots `p` или рассчитанного network hashrate. `/api/v1/hashrate-history` показывает историю пула и не доказывает динамику сети.
7. Если исторического network target нет, напиши: `текущий уровень рассчитан; изменение сети за период не доказано`. Не угадывай изменение по доходности, числу воркеров или цене монеты.
8. Если есть доступ к рабочему каталогу, сохраняй сырой timestamped snapshot pool target, pool hashrate и price source для будущего сравнения; не перезаписывай предыдущие snapshots.

### Этап 4. Полный рынок Clore

1. Используй полный `GET https://api.clore.ai/v1/marketplace`. Число исходных серверов — не результат поиска.
2. Отфильтруй недоступные, US, stop-list, неподдерживаемые CMP/AMD для CUDA-бинарника, подозрительные смешанные риги и варианты короче 24 часов.
3. Для каждого кандидата проверь server ID, GPU count/model/VRAM, `specs.stock_pl`, длину массива PL, `specs.stock_oc`, locks/offsets, PCIe, CPU/AVX2, RAM/disk, country, reliability, число отзывов, max duration и USD on-demand цену всего сервера. `specs.pl` используй только как вспомогательное поле.
4. Не считай высокий `stock_pl` доказательством производительности. Учитывай locks. Не отвергай PCIe x1 или Celeron автоматически: они у нас работали.
5. Хешрейт бери из подтверждённой исторической таблицы навыка с поправкой на реальный PL/locks. Для неизвестной конфигурации показывай диапазон и risk discount, а не точное придуманное число.
6. Рассчитывай expected и conservative kp/s, gross, rent, net, `margin = net / rent × 100%`, break-even NOCK price, сценарий `$0.025/NOCK`, источник каждого входа и confidence.
7. Сортируй по conservative net, затем по margin, reliability/reviews и длительности. Не ослабляй критерии молча. Если достойных вариантов нет — так и напиши.

## Формат результата

1. Короткий итог.
2. Таблица состояния источников.
3. Таблица всех активных воркеров и отдельная сверка активных Clore-заказов.
4. Текущий network/pool/yield и доказанная либо недоказанная динамика.
5. Одна компактная таблица кандидатов Clore.
6. Решение по кандидату: `PROCEED TO MANUAL REVIEW`, `NEAR-MISS` или `REJECT`, с причиной.

Всегда отделяй `FACT`, `CALCULATED`, `ESTIMATE` и `UNAVAILABLE`. Не называй reference-цену исполнимой и не называй историческую строку активным воркером.

## Управление выполнением

- Не держи пользователя без обновления дольше 2–3 минут: сообщай текущий этап, количество обработанных записей и блокер.
- Не запускай бесконечные или многократные поисковые циклы. Один полный проход API и один предусмотренный fallback достаточны.
- На команду `остановись` немедленно прекрати циклы, фоновые задачи и браузерные действия, ничего нового не запускай и ответь одной короткой сводкой уже полученных фактов.
- Поиск и расчёт не являются разрешением на аренду или изменение серверов.

Начни с этапа 1. После проверки источников выполни этап 2 полностью и покажи сверку воркеров/заказов; затем без дополнительного вопроса переходи к этапам 3–4, если пользователь не остановил выполнение.
